# Operations

How antares is run, watched and recovered. The desktop app is the product; the
engine and the HTTP client are its transport, and both are observable without
a debugger.

## Runtime surface

- The engine owns one loop on one thread, plus one resolver thread, plus a pool
  of parse workers. The loop is single-threaded by contract, so connection state
  takes no lock. `ANTARES_IO_BACKEND` picks the backend (`kqueue` by default, `poll`
  as the escape hatch) and is read once at startup.
- `ANTARES_ALLOCATOR=system` swaps mimalloc for the system allocator when a
  profile disagrees with the build.
- `SIGTERM` and a window close both call `quit()`. The drain runs after
  `app.exec()` returns, pumping the loop with a deadline; a stuck peer logs
  `warn` and does not hang the quit.
- Nothing binds a port. The client dials out; the app never listens.

## Health

`EngineStats` exposes `submitted`, `completed` and `failed` per backend.
`ClientStats` exposes `opened`, `reused`, `retired`, `retries`, `timeouts`,
`tlsFailures` and `idleClosed`. A rising `opened` with a flat `reused` means the
pool is not settling; a rising `failed` means the loop is stalling.

## Failure handling

A failed connection is closed, never reused. `cancel()` is idempotent and
releases the wire. After `stop()` returns, no completion starts — a shutdown
never races a callback.

## Recovery

Restart the app. There is no persistent state to repair: the pool is memory
only, and `~/.cache/antares/deps` is regenerated by CMake.

## Rollback

A bad build rolls back by checking out the previous commit and reconfiguring;
`build/` is disposable and `~/.cache/antares/deps` is content-addressed, so a
rollback never needs a manual clean.

## Escalation

A hang is diagnosed by sampling the process: the loop thread is named
`antares.io`, so it is identifiable in a sample without reading code. A hang
with that thread inside `kevent` and work queued means the wakeup pipe was not
armed — a defect, not a slow peer.
